# ADR 0028: Living Frontier map and native-system boundary

- Status: Accepted
- Accepted: 2026-07-29
- Protocol effect: none
- Authority effect: none
- Product effect: make the living Frontier map the primary product surface
- Package effect: keep Vela Math source-local until two consumers and deleted
  duplication earn extraction
- Service effect: no Registry, Atlas service, graph database, hosted authority,
  second writer, or new repository

## Context

Vela has a precise integrity boundary and a growing body of bounded evidence.
Its active work nevertheless risked treating the transition protocol,
benchmarks, and reader plumbing as the product while the scientific territory
remained difficult to understand and continue.

The product must answer, from exact current state:

```text
What is known, checked, recorded, disputed, or missing?
Why does each Claim have its current Standing?
Which source and coverage limits apply?
What failed work should not be repeated?
What is the next valid bounded Target?
What changes after an authorized Decision?
```

Native mathematical systems already own proof languages, kernels, packages,
corpora, and identifiers. Generic workbench products already own prompts,
sessions, checkpoints, and activity history. Vela should bind these systems,
not replace them.

## Decision

### 1. Make the hierarchy explicit

```text
protocol  -> integrity layer
map       -> product
verified frontier movement -> outcome
```

The public loop remains:

```text
map -> target -> run -> verify -> commit -> compound
```

The protocol remains load-bearing because it makes the map exact and the next
action safe. Record count, node count, run count, workflow completion, and
model activity are not success metrics.

### 2. Build the first complete map from existing owners

The first product proof is the Erdős corpus map and one complete Erdős 1056
problem map in the existing Observatory. They are deterministic, read-only
projections from the canonical Frontier repository and disclose their exact
source roots, projector identity, coverage, omissions, and current Target.

No new canonical map object, repository, ingestion service, graph database, or
writer is authorized. A disposable manifest is permitted only if the existing
derived files cannot bind coverage and projector identity exactly.

### 3. Require visible remapping

A completed loop is:

```text
Target
-> Attempt
-> Submission
-> independent Verification
-> authorized human Decision
-> Event and replayed Standing
-> rebuilt map and semantic diff
-> next Target derived from the new head
```

The product fails closed when accepted coverage does not update, a closed
Target remains offered, the next Target overlaps completed work without a
declared reason, a projection cites superseded state as current, or verifier
success is presented as acceptance.

### 4. Keep Vela Math a profile over native systems

The first source-local profile may project:

```text
Problem
MathematicalClaim
Formalization
MathematicalResult
Obligation
StatementFidelityReview
```

These views resolve to current Vela roots or exact native identifiers. They
add no reducer rule, authority effect, global ontology, proof language, or
dependency resolver. Lean, Lake, Mathlib, Formal Conjectures, OEIS, LMFDB, and
other native systems remain sovereign.

Shared extraction requires two maintained consumers, deterministic offline
generation, native-identity preservation, explicit loss reports, and deletion
of more maintained duplication than the package adds.

### 5. Use reference, snapshot, and admission precisely

- **Reference** binds a stable native identity.
- **Snapshot** retains exact bytes and environment needed for reproduction.
- **Admission** routes a bounded proposed transition through local
  Verification and authorized Decision.

Reference does not imply availability. Snapshot does not imply Verification.
Verification does not imply admission. A foreign Decision never imports local
Standing.

Cross-system Bridges declare an exact source and target, a bounded consequence
tier, assumptions, unsupported constructs, and a loss report. Similarity,
embeddings, graph position, or shared notation never establish equivalence or
transport authority.

### 6. Keep external activity recorders optional

External activity recorders such as Entire may preserve session context and
checkpoints in the activity plane. They do not replace Git, a Canopus Run,
Verification, or Vela. They are not required for replay and receive no
credential or authority access.

No adapter or public schema is authorized before a private, noncanonical,
metadata-only pilot improves one preregistered continuation or
evidence-location metric by at least 20 percent without reducing correctness,
privacy, canonical commit control, or removability. A neutral or negative
result deletes the provider-specific experiment.

### 7. Measure four claims separately

1. **Execution lift:** verifier-passing bounded artifacts per all-in cost and
   expert-minute.
2. **State lift:** correct review, correction comprehension, and evidence
   location per reviewer-minute.
3. **Inheritance lift:** time to first useful downstream action, duplicate
   work avoided, and correction awareness after substitution.
4. **Map performance:** coverage disclosure, stale-state rate, valid Target
   rate, Decision-to-remap latency, and cold-user comprehension.

Evidence for one claim does not establish the others. The north star is
verified frontier expansion per unit of scarce expert judgment.

## Immediate gates

1. Finish the bounded current-state compaction and remove predecessor runtime
   compatibility after four clean-clone activations.
2. Normalize the minimum map projection from existing Erdős data.
3. Expose all 1,217 catalogued problems with disclosed coverage.
4. Build the complete Erdős 1056 map and exact next-action handoff.
5. Complete the next non-overlapping bounded Target through Decision.
6. Rebuild the map and prove the semantic before/after diff and Target update.
7. Run an uncoached cold-user test.
8. Repeat the pattern on the Formal Conjectures slice.

Compaction is a bounded prerequisite, not a public product milestone.
Whitepaper, package, Registry, Atlas, and cross-domain claims remain gated by
their registered evidence.

## Rejected alternatives

- **Treat the protocol or benchmark suite as the product.** Rejected because
  users need a legible scientific territory and next action.
- **Build a universal mathematical DSL or ontology.** Rejected because native
  systems already own semantics and current recurrence has not earned it.
- **Ingest all external mathematics into one Vela store.** Rejected because
  reference, selective snapshot, and local admission preserve sovereignty and
  reduce staleness.
- **Build a Registry or Atlas now.** Rejected until reusable packages and
  exact cross-Frontier correction produce measured continuation value.
- **Make Entire mandatory or canonical.** Rejected because activity context is
  optional, sensitive, incomplete, and unrelated to scientific authority.
- **Add another repository or service for the map.** Rejected because the
  Frontier repositories and Observatory already own the canonical data and
  read surface.

## Consequences

The active campaign is reprioritized around one visible
map-to-advance-to-remap loop. Protocol work is limited to blocking integrity
defects and the already bounded pre-release compaction. Vela Math and external
activity integrations remain source-local experiments with deletion gates.
The larger federation and whitepaper theses stay explicit but cannot outrun
the map, correction, transfer, and cold-use evidence.
