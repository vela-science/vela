# VELA-RC-1 R5 product and Observatory semantic-legibility audit

Date: 2026-08-26 (America/Toronto)

## Verdict

`HOLD — PRODUCT SEMANTICS`

Vela Core and the current Workbench make Proposal, scoped Verification,
Decision, Standing, correction history, and replay separate enough to operate
without inventing authority. The public read product does not yet qualify for a
release-facing claim of the same semantic boundary:

1. it renders `strict pass` from a projection generated by Vela `0.977.3`, whose
   exact read path did not enforce the independently pinned sequence-one
   authority root now required by Protocol 1; and
2. it labels a count containing agent-performed Decisions as `Human authority`.

Both defects are in the read-only sibling product. This lane changed no sibling
repository, protocol object, schema, product layout, package, version, tag,
deployment, or release state.

## Surface audit

### Vela Core

The Core surfaces preserve the product loop and distinct semantic axes:

- `vela --help` exposes `init`, `status`, `claims`, `submit`, `show`, `why`,
  `review`, `replay`, and `log` without introducing a second product ontology;
- `vela review --help` keeps the Inbox, pending Proposal, Verification, and
  attributed accept/reject Decision separate;
- `docs/CLI.md` states that Verification changes no Standing, Decision is the
  authority boundary, and accepted correction or supersession retires one exact
  predecessor while preserving history;
- `examples/neutral-replay` presents the exact sequence
  `Submission -> scoped Verification -> attributed Decision -> admitted Events
  -> accepted Standing -> strict replay`; and
- the repaired governed-read boundary refuses missing, malformed, or mismatched
  OS-account pins before returning Standing or authority history.

No Core semantic-legibility issue was found.

### Problems / current Observatory read surface

The current product is exposed through Problems routes rather than a separately
named Observatory application. Its detailed surfaces are unusually explicit:

- the Repository summary places Standing, Integrity, Activity, and Decisions on
  separate axes;
- the Proposal page distinguishes the producer package, scoped Verification
  Records, the repository-authority Decision, and applied Event;
- the Claim ledger separates current accepted and retained superseded Claims;
- Claim detail states that scoped checks are assurance and are not Claim
  Standing, links the Decision, and renders `corrects` to the exact predecessor;
- Problem Overview separates source status, `Decision here`, current Result,
  and `Still unresolved`; and
- Problem History retains prior states, corrections, performers, checks, and a
  visible Submission-to-Decision-to-Result evidence flow.

Those surfaces satisfy the object and history distinctions except for the two
exact findings below.

### Vela Workbench

Workbench preserves the write/readback boundary in both product copy and
tests. `src/TrancheThree.tsx` refuses to infer a Proposal, Verification,
Decision, or Standing from stale Inbox state; labels Verification output as
non-authoritative and says `Standing remains separate`; and renders a separate
`Actual Decision / Event / Standing readback` that says the Verification
outcome is not that Standing. It then makes Git publication and downstream
projection verification a separate operator handoff.

The Workbench release record still pins Core `0.977.3`. That release alignment
is part of the exact-generator problem in R5-F001 and the separate packaging
lane; it is not evidence that Workbench's displayed object roles are confused.
No additional Workbench semantic-legibility issue was found.

## Findings

### R5-F001 — `RELEASE-BLOCKING CONFUSION`

**Public `strict pass` does not include the current Protocol 1 independent trust
selection.**

The live Repository summary renders `replay verified` and `strict pass` from
`apps/problems/src/components/vela/repository-context.tsx:111-124`. The live
deployment manifest binds the projection to:

- generated at `2026-08-19T14:43:50-04:00`;
- Vela `0.977.3`;
- macOS generator digest
  `sha256:3a1173918bdcb887155bab681411bf5e9ff64d925fe1b50369ac37ab020b94ad`;
- projection release root
  `sha256:c9d14c459c518937e758918b5897dc3b22f1a55f07739afe99502f5b046c907a`;
  and
- source Repository commit/tree
  `2415f78e850aeee50afdca525c6f2e0ea606f207` /
  `46748bacbeab8bbf0305591d71d119598af5c4eb`.

The exact Vela `v0.977.3` source calls `load_repository_at` directly for
`status`, review reads, and other governed reads. Commit
`ad2a4516078525025d05bd461b550ed5b8e35971` is the later change named `Fail
closed on unpinned governed reads`; it introduced `load_trusted_repository_at`
and `verify_trusted_repository_at` for those surfaces. The campaign's original
R1 reproduction independently records that the old path could return
`strict: pass` without consulting the pin.

Current Protocol 1 defines strict replay to include the independently pinned
sequence-one authority root and to refuse a missing, malformed, or mismatched
OS-account pin. The Web release pipeline currently verifies `status.integrity`
from the configured `0.977.3` binary, but its source registry and acquisition
path contain no independent authority-root selection. The UI is therefore
truthful about what its generator returned but misleading about the current
meaning of `strict pass`.

**Owning repository and minimal fix specification:**

- repository: `/Users/williamblair/personal/vela-web`;
- current fetched commit: `b7de325c0c59bb0d83f0f00c8f181dcf2218def2`;
- deployed commit: `a4876c88d5037ecbdf8627262d49bcb10cdad72d`;
- exact paths:
  `packages/projection-data/config/vela-release.v1.json`,
  `packages/projection-data/src/registry.ts`,
  `scripts/release-problems.mjs`, and
  `packages/projection-data/scripts/projection-builder.mjs`.

After R6 authorizes one exact released Core digest, bind the projection to that
digest and require an independently qualified sequence-one root for every
registered Vela Repository before the first governed read. Add a release-path
negative test proving projection generation refuses a missing or mismatched
OS-account pin, then regenerate and activate the projection before rendering
`strict pass`. Do not alter the UI meaning, add a second integrity mode, or
weaken Core's trust model. Version selection, packaging, signing, publication,
and deployment remain outside R5.

### R5-F002 — `SEMANTICALLY MISLEADING`

**An actor-neutral Decision count is labelled `Human authority`.**

At the exact deployed commit,
`apps/problems/src/components/vela/repository-context.tsx:138-140` labels
`loop.decisions` as `Human authority` and describes the value as retained
authorized Decisions. The same source is at lines 137-140 on fetched
`origin/main`, and
`apps/problems/src/components/vela/repository-context.test.tsx:50-54`
explicitly locks the human-only label.

The same deployment's Proposal detail calls an accepted action `Agent Decision`
and identifies an agent performer. The Repository page's retained Decisions
also include agent actor classes. Protocol 1 allows one authorized human or
agent performer. The label therefore assigns a false actor class to the value
it counts.

**Owning repository and minimal fix specification:**

- repository: `/Users/williamblair/personal/vela-web`;
- current fetched commit: `b7de325c0c59bb0d83f0f00c8f181dcf2218def2`;
- deployed commit: `a4876c88d5037ecbdf8627262d49bcb10cdad72d`;
- exact paths:
  `apps/problems/src/components/vela/repository-context.tsx` and
  `apps/problems/src/components/vela/repository-context.test.tsx`.

Replace `Human authority` with the actor-neutral label `Authorized Decisions`,
retain the existing count and layout, and update the test to require that
label. Exercise the component with an agent-class Decision so the summary
cannot imply a human actor for a mixed or agent-performed count. No schema,
protocol field, dashboard, or visual redesign is needed.
