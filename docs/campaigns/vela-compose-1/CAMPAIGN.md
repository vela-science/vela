## Operating mode

```text
BUILD -> USE -> MEASURE -> NOTICE -> THEORIZE ONLY IF REALITY FORCES IT
```

Success levels are:

1. protocol proof: governed transitions, replay, correction, rejection,
   receipts, branch isolation, and accounting work reliably;
2. cumulative-science proof: governed Standing materially improves a later
   machine's continuation over competent ordinary artifacts and a neutral
   information-equivalent export;
3. control-defeating anomaly: a repeated objective effect survives all frozen
   information, resource, packaging, retrieval, hidden-state, model, leakage,
   and evaluator controls.

Level 1 is valid success. Level 3 triggers freeze, one unchanged replication,
and user notification—not theory generation.

## Repository boundary

Vela Core owns portable objects, canonical bytes, roots, repository authority,
Decision admission, events, replay, CLI contracts, and conformance. It does not
own scientific campaigns, Lean proofs, biological dossiers, run schedulers,
agent traces, or experimental metascience. Those stay in source-owning
repositories. Core extraction requires two maintained consumers and must delete
more duplication than it adds.

## Canonical semantic mapping

Campaign language maps onto the current implementation:

```text
producer work -> authenticated Submission -> repository Proposal
scoped check -> Verification Record
attributed acceptance/rejection -> authorized Decision
admitted transition -> semantic Event inside authority history
current scientific state -> deterministic Standing projection
```

Verification alone cannot change Standing. Git publication, signatures, green
checks, model output, and source merges are not acceptance. Standing is derived
from admitted history; correction and supersession append rather than rewrite.

## Workstreams and gates

- T1 Kernel + Conformance and T2 Receipts + Replay start after Phase 0.
- T3 starts only after T1/T2 interfaces and invariants are qualified.
- T4 uses stable general APIs and may not special-case Lean into Core.
- T5 planning may inspect source-owned work after Phase 0; substantive execution
  waits for kernel and replay qualification.
- T6 requires T3 apparatus plus a qualified vertical and a preregistered R/V/E
  design.
- T7 integrates only supervisor-approved, protocol-qualified behavior.

Workers never merge themselves or make campaign-level semantic decisions.
Supervisor dispositions are exactly `MERGE`, `MERGE WITH FIX`, `RETURN TO
WORKER`, or `REJECT`.

## Campaign stopping rules

Stop expansion and report if core invariants require major redesign, replay
needs hidden mutable state, real verticals require pervasive domain-specific
exceptions, a valid R/V/E experiment shows no value beyond neutral export, Vela
systematically worsens scientific-state assumptions, or a control-defeating
anomaly occurs.
